# 全自动自托管弹幕服务设计

日期：2026-08-11  
状态：总体方向已确认，待实施计划评审  
目标用户：使用 Forward、SenPlayer 和多个第三方 Emby 服务器的单人用户

## 1. 背景

用户在 iPhone、iPad 和 Mac 上通过 Forward、SenPlayer 播放多个第三方 Emby 服务器中的影视内容。用户无法管理这些 Emby 服务器，也不能在其中安装插件、配置 Webhook 或读取媒体目录，但拥有一台位于美国达拉斯、可全天运行的 x86_64 VPS，并已安装 Docker、Caddy，域名托管在 Cloudflare。

目标是在该 VPS 上部署兼容弹弹 play API 的私人弹幕服务，让播放器只需填写一个 API 地址，便可自动完成匹配、搜索、下载、缓存、校时、异常片源拆分、维护、备份、更新和故障回滚。

系统以最新版稳定版 Misaka Danmu Server 为核心，并增加一个定制的“弹幕自动驾驶”旁路服务，处理 Misaka 常规流程无法可靠覆盖的补档、改名、长时间垫片、合集和时间轴错位场景。

## 2. 设计原则

1. **无人值守优先**：初次输入必要的域名、密码、Token 和 Cookie 后，日常操作不要求用户进入后台。
2. **准确优先于数量**：优先选择与当前季、集、版本一致的来源，再考虑合并更多来源。
3. **不阻塞播放**：低置信度任务也会给出最佳可用结果；后台继续重试和改进，不让确认页面卡住播放流程。
4. **保留原始数据**：任何裁剪、偏移、拆分和合并都可重算，不覆盖唯一的原始副本。
5. **不绕过访问控制**：只使用公开接口或用户 Cookie 本来有权访问的数据，不规避付费、会员或地区权限。
6. **公网最小暴露**：播放器 API 可公网访问，管理接口、数据库和内部控制接口不直接暴露。
7. **可验证、可回退**：更新前备份，更新后健康检查；失败自动回滚，并提供一条命令手动回滚。
8. **不过度请求源站**：缓存、限速、指数退避和随机抖动共同减少封禁风险。

## 3. 范围

### 3.1 包含

- Forward 和 SenPlayer 的弹弹 play 兼容 API。
- Misaka Web 管理后台、弹幕库、Token、过滤和来源配置。
- 动画、电影、国剧、综艺、韩剧、日剧等内容类型。
- B站、腾讯、爱奇艺、优酷、芒果及 Misaka 可安装的其他合法弹幕源。
- 自动别名、季集识别、来源排序、重复弹幕处理和下一集预下载。
- B站补档、改名、合集、长时间垫片和片头广告的自动时间轴修正。
- 自动备份、异地备份接口、自动更新、健康检查、通知和回滚。
- Caddy 与 Cloudflare 配置模板。
- Docker Compose、配置模板、运维脚本、测试和小白教程。

### 3.2 不包含

- 修改或控制第三方 Emby 服务器。
- 下载、存储或转发影视视频本体。
- 绕过平台付费、会员、版权或账号访问限制。
- 保证所有故意伪装且没有任何时间线信号的来源 100% 正确。
- 在弹弹 play XML/JSON 和播放器能力之外完整还原 B站高级蒙版、互动、路径动画等特效。

普通滚动、顶部、底部、颜色、时间、文本和基础字号会尽量原样保留；高级效果最终能否显示取决于 Forward/SenPlayer 的渲染能力。

## 4. 总体架构

```text
Forward / SenPlayer
        |
        | HTTPS + 每设备独立 Token
        v
Cloudflare DNS / 可选代理
        |
        v
Caddy（宿主机现有实例）
        |
        +---- 公共弹幕路由 ----> Autopilot API Gateway
        |                            |
        |                            +----> Misaka 弹弹兼容 API
        |                            +----> 异常识别与异步任务队列
        |
        +---- 管理路由 --------> Basic Auth ----> Misaka Web UI
                                             
Docker 内部网络
  - Misaka Danmu Server
  - MySQL（不映射公网端口）
  - Autopilot（不映射公网端口）

持久化数据
  - Misaka 配置与弹幕库
  - MySQL 数据
  - Autopilot 原始弹幕、派生结果、置信度和审计记录
  - 本地备份 + 可选加密异地备份
```

### 4.1 Misaka

Misaka 负责常规匹配、来源插件、弹幕库、API Token、过滤、任务队列、后备搜索、顺延和预下载。部署时解析其 GitHub 最新稳定版本，排除 beta、alpha、rc 和预发布版本，并将实际镜像版本与 digest 写入锁定文件。

Misaka 的外部控制 API 用于自动导入 XML、搜索、读取或覆盖弹幕、管理分集和查询任务。Autopilot 不直接写 Misaka 数据库，降低升级耦合和损坏风险。

### 4.2 MySQL

使用 Misaka 官方支持的 MySQL 大版本并固定镜像版本，不对 MySQL 使用 `latest`。数据库只在 Docker 内部网络开放，配置健康检查、合理的内存上限和字符集。数据库升级与 Misaka 应用更新分离。

### 4.3 Autopilot API Gateway

Gateway 对播放器透明代理兼容 API，同时记录经过脱敏的匹配上下文：文件名、季集信息、请求结果、任务状态和来源质量。Token 不进入普通访问日志。

它负责：

- 规范化第三方 Emby 返回的混乱文件名。
- 使用作品别名、罗马字、中文译名、平台避审名和常见错别字扩展搜索。
- 观察 Misaka 的常规匹配结果和后台任务。
- 在常规来源缺失、时长异常或质量不合格时启动异常片源流程。
- 对原始弹幕进行时间轴分析、裁剪、拆分、偏移、去重和导入。
- 为低置信度结果添加标记并发送通知，但不等待人工确认。

Gateway 必须保持接口透传：任何自身异常都自动旁路到 Misaka，不能因为附加功能导致播放器完全没有弹幕。

## 5. 常规自动匹配流程

1. 播放器携带独立 Token 请求匹配或搜索。
2. Gateway 解析文件名中的标题、年份、季、集、分辨率、发布组和版本标记。
3. 请求 Misaka 本地弹幕库。
4. 若没有结果，Misaka 的匹配后备自动搜索已启用来源。
5. 候选结果按作品一致性、季集一致性、来源可靠度和历史成功率排序。
6. 最佳来源自动导入并缓存。
7. 当前集返回后，后台预下载下一集。
8. 失败任务按指数退避重试；命中明确的永久错误时停止重试并通知。
9. 后续播放优先命中本地缓存，不重复抓取源站。

由于用户不控制 Emby，系统不能依靠 Emby Webhook 预先知道完整媒体库。首次播放是主要触发点，下一集预下载和最近作品刷新用于减少等待。

## 6. 来源选择与合并

来源采用分层策略：

1. 与当前作品、季、集直接对应的官方单集来源。
2. 同一剪辑版本、时间轴可校正的其他平台单集来源。
3. 可可靠拆分的官方合集或补档合集。
4. 改名、伪装、reaction 或带长时间垫片的来源。
5. 只有模糊语义和时长推断的低置信度来源。

默认不盲目合并多个平台。只有时间轴相近且重复率可控时才自动合并；否则选择最高质量的单一来源。去重综合文本规范化、时间窗口、发送模式和颜色，而不是只按文本删除。

平台优先级、是否合并、输出数量上限、广告词和剧透词过滤均可在后台切换。过滤规则变更后，系统自动重建派生缓存，无需重新抓取原始弹幕。

## 7. 广告与版本时间差

### 7.1 动态平台广告

多数流媒体片头广告不属于正片媒体时间轴，平台在广告结束后从正片 0 秒开始计时。这类广告不会进入弹幕时间，通常无需处理。

### 7.2 烧录在时间轴中的前置内容

若弹幕来源把广告、垫片、倒计时或 reaction 片段与正片放在同一时间轴，而 Emby 版本没有这些内容，Autopilot 自动估算正片起点并对弹幕做负偏移。

### 7.3 Emby 版本自身不同

若 Emby 文件比弹幕来源多一段片头，则需正偏移。由于多个第三方 Emby 服可能采用不同剪辑，服务端不把一次偏移无条件应用到所有服务器。能区分文件 hash 或稳定文件标识时，偏移按版本保存；无法区分时保留播放器本地偏移作为最后兜底。

### 7.4 中段删减

单一全局偏移无法修复中段删减。系统使用分段时间映射：在删减点前后分别计算偏移，再生成连续的目标时间轴。

## 8. 异常补番与长垫片自动处理

### 8.1 触发条件

任一条件可触发异常分析：

- 候选来源时长明显大于单集或整季预期时长。
- 标题含“全集、合集、完整版、reaction、补档、充电、看封面”等特征。
- 一个分 P 承载多集内容。
- 前段弹幕密度长期极低，随后出现显著跃迁。
- 弹幕中出现“终于开始、正片开始、等了两小时、第 X 集”等语义锚点。
- Misaka 普通候选为空，但搜索到可访问的长视频来源。

### 8.2 信号优先级

自动分析按成本由低到高逐层使用：

1. 平台公开元数据：时长、分 P、章节、标题、简介。
2. 作品元数据：季数、集数、标准单集时长、播出顺序和别名。
3. 弹幕统计：密度变化、时间空洞、峰值、重复片头模式。
4. 弹幕语义：正片、集数、片头、片尾和等待类表达。
5. 用户 Cookie 有权访问时的低码率音频、关键帧或故事板分析。
6. 可选 AI：只用于标题语义、锚点复核和低置信度解释，不作为唯一切点依据。

正常情况下不下载完整高清视频。只有前四层不足时才取低带宽分析素材，并设置严格的临时空间和自动清理上限。

### 8.3 切点推断

系统建立候选切点集合，通过动态规划或约束优化选择：

- 正片起点；
- 每集起止时间；
- 片头、片尾和中段删减造成的局部偏移；
- 与作品预期集数、单集时长最相符的一组边界。

每个结果产生 0–100 的置信度和可解释证据。高、中、低置信度均自动执行，但策略不同：

- **高置信度**：自动裁剪、拆集、导入并成为首选来源。
- **中置信度**：自动导入，若存在正规单集来源则把正规来源放在前面。
- **低置信度**：若无更好来源仍自动导入最佳估计，同时通知用户并保留醒目标记；后台继续寻找替代来源。

### 8.4 用户给出的样本

样本 `BV1HS6ZBiE43` 总时长约 4:48:03、单分 P，平台章节为空。弹幕在约 2:00:00 出现“等了两个小时终于开始了”等强锚点；剩余约 2:48:03，与 8 集、每集约 21 分钟高度吻合。因此预期流程是：

1. 自动判定前约两小时为垫片。
2. 从正片起点开始，根据预期 8 集、弹幕峰值和重复片头模式求取 8 组边界。
3. 生成 8 份时间归零的弹幕。
4. 自动映射到对应作品与季的 E01–E08。
5. 通过 Misaka 外部控制 API 导入。
6. 保存原始 XML 和切点证据，以便以后自动重算。

如果该视频受到付费或其他权限保护，系统只在用户 Cookie 已合法获得访问权时使用；不会尝试绕过权限。

## 9. 自动学习与纠错

- 用户在后台修改作品、来源、集数或切点后，修改会存为高优先级本地规则。
- 相同别名、UP 主、来源模式和版本特征再次出现时自动复用。
- 自动结果被替换或删除时降低对应规则与来源的历史评分。
- 若播放器只在本地调整偏移且不向服务端上报，服务端无法自动得知该修正；文档会说明这一客户端限制。
- 所有规则带版本号，可在算法升级后批量重算而不破坏人工确认项。

## 10. 网络与海外部署

达拉斯 VPS 是否能稳定访问国内视频源必须在部署时实测。预检脚本会测试 DNS、TLS、IPv4/IPv6、目标 API、响应时延、地区限制和限流状态，并生成可读报告。

路由策略：

1. 能直连的来源直接访问。
2. 仅对失败来源使用 HTTP/SOCKS5 代理，不让数据库、Caddy 或全部系统流量走代理。
3. 代理失效时自动退回可用来源并通知。
4. Snell 若只是部署在同一台达拉斯 VPS 上，不会改变出口地区；只有代理出口位于合适地区时才有帮助。

基础系统免费。可能产生额外费用的部分只有可选大陆/港澳台出口代理、AI API、异地对象存储以及域名本身。

## 11. 公网、安全与隐私

- 建议两个子域名：一个播放器 API 域名，一个管理域名。
- Caddy 只代理必要路径；MySQL、Misaka 外部控制 API 和 Autopilot 管理端只留在 Docker 内网或本机回环地址。
- 管理域名同时使用 Caddy Basic Auth 和 Misaka 登录。
- 每台设备使用不同的 Misaka Token，可单独吊销、统计和限额。
- `.env`、Cookie、数据库密码、Cloudflare Token、通知 Token 和 API 密钥不提交 Git，文件权限为 `0600`。
- 访问日志不记录 URL 中的 Token；请求体和响应体日志默认关闭或脱敏。
- Cookie 支持到期检测和通知，不在通知内容中输出 Cookie 值。
- 容器默认以非 root 用户运行，移除不需要的 capabilities，根文件系统尽量只读。
- 不把 Docker Socket 挂入长期运行的容器。更新由宿主机受限脚本和 systemd timer 执行。
- Cloudflare 代理为可选项；无论是否启用，源站只开放 Caddy 所需端口。

## 12. 自动通知

通知适配层支持 Misaka 已有渠道及通用 Webhook。部署时可选择 Telegram、Server酱、Bark/ntfy 兼容 Webhook 或仅写本地日志。

默认只通知需要关注的事件：

- Cookie 即将或已经失效；
- 连续来源访问失败或地区限制；
- 低置信度异常片源已自动处理；
- 自动更新成功、失败或回滚；
- 备份连续失败；
- 磁盘空间、数据库或 API 健康异常。

普通成功匹配不发送通知，避免打扰。

## 13. 自动备份、恢复和保留策略

备份包括：

- MySQL 一致性逻辑备份；
- Misaka 配置、弹幕库和来源配置；
- Autopilot 原始数据、派生数据、规则和审计记录；
- 实际部署版本与镜像 digest 锁定文件。

策略：

- 每日自动本地备份，默认保留 14 份。
- 每次更新前创建带版本标记的备份，默认保留最近 5 份。
- 每周执行一次自动恢复演练到临时数据库并验证关键表，而不是只检查压缩包存在。
- 支持用 restic/rclone 将加密备份上传到用户选择的 S3/R2 等异地存储；未配置远端时明确显示“只有本机备份”的告警。
- `backup.sh`、`restore.sh` 和 `rollback.sh` 均使用锁，防止与更新或另一个备份并发。

## 14. 自动更新与回滚

用户要求始终跟随最新稳定版 Misaka。更新流程每日自动检查一次稳定 Release：

1. 排除预发布、草稿、beta、alpha 和 rc。
2. 记录当前版本和镜像 digest。
3. 执行预检、磁盘检查和更新前备份。
4. 拉取目标镜像并锁定 digest。
5. 仅重建需要更新的服务。
6. 运行数据库、Web UI、播放器 API、Misaka 外部控制和 Gateway 冒烟测试。
7. 观察短暂稳定窗口。
8. 失败则自动恢复旧镜像；若数据库迁移不兼容，同时恢复更新前数据库备份。
9. 成功或回滚后发送通知。

另外提供一条命令回滚到最近成功版本，也可指定历史版本。MySQL 不随 Misaka 日常更新自动跨大版本升级。

Autopilot 自身由本项目源代码构建并锁定版本；在没有可信发布仓库之前不会从未知远端自动替换代码。

## 15. 可观测性与自愈

- Docker healthcheck 检查 MySQL、Misaka、Gateway。
- systemd 负责开机启动、异常重启、定时备份和定时更新。
- 综合健康检查从 Caddy 外部入口模拟一次无敏感数据的 API 调用。
- 磁盘空间不足时先清理临时媒体分析文件和过期缓存，不自动删除最新备份或原始规则。
- 源站失败采用指数退避、熔断和半开探测，防止持续请求导致封禁。
- 每周生成匹配成功率、低置信度数量、来源失败率和备份状态摘要。

## 16. 配置与自动化边界

“全自动”指完成初始必要配置后无人值守运行。下列信息无法安全猜测，部署前仍需用户提供一次：

- API 与管理子域名；
- 管理员密码和设备 Token，或允许脚本自动生成；
- B站等平台 Cookie；
- 可选元数据、AI、通知和异地备份凭据；
- 若达拉斯直连失败，可用代理的地址和凭据。

脚本会自动生成所有可生成的密钥，并只把结果写入权限受限的本地文件。不会要求用户手写 Docker Compose 或数据库命令。

## 18. 测试策略

### 18.1 单元测试

- 文件名和季集解析。
- 别名扩展与避审名规范化。
- B站 XML 解析和时间字段保真。

- 日志脱敏、Token 和 Cookie 不泄漏。
- 稳定版本筛选，确保预发布版本不会被选中。

### 18.2 合成异常样本

用合成弹幕构造以下场景，不把第三方完整弹幕数据提交仓库：

- 两小时无关垫片后接 8 集正片。
- 普通平台前置广告。
- 中段删减导致分段偏移。
- 多平台重复弹幕。
- 没有章节、只有弱语义信号的低置信度来源。

### 18.3 集成测试

- Docker Compose 配置解析和容器健康检查。
- Gateway 到 Misaka 的透明代理与故障旁路。
- Misaka 外部控制 XML 导入和弹幕覆盖。
- MySQL 备份后恢复到临时实例。
- 模拟新版本成功更新、健康检查失败和自动回滚。
- Caddy 路由确保内部控制端点无法从公网访问。

### 18.4 手动兼容验收

由于 Forward 和 SenPlayer 是闭源客户端，最终仍需在各自最新版上各做一次真实设备验收：自动匹配、手动搜索兜底、Token、颜色/模式、缓存和错误提示。验收通过后其配置步骤写入教程。

## 19. 验收标准

1. 一条部署命令可生成密钥、启动服务并给出下一步配置提示。
2. Forward 与 SenPlayer 能通过 HTTPS API 自动取得弹幕。
3. 常规剧集首次播放自动匹配，后续命中缓存并预下载下一集。
4. 两小时垫片加 8 集合集的合成样本能自动识别起点、拆为 8 集并正确归零。
5. 低置信度任务不阻塞播放，能自动采用最佳结果并通知。
6. 广告前置偏移和中段删减样本可正确转换时间轴。
7. API、数据库和管理面不发生不必要的公网暴露，日志不泄漏秘密。
8. 日备份和更新前备份自动执行，恢复演练可通过。
9. 模拟错误版本时系统自动恢复旧服务和必要的数据备份。
10. 用户可用一条命令回滚到最近成功版本。

## 20. 主要风险与应对

| 风险 | 应对 |
| --- | --- |
| 海外 IP 无法访问部分国内来源 | 部署预检、按来源代理、熔断和来源降级 |
| 平台接口或反爬策略变化 | 来源插件隔离、版本锁定、健康监控、保留原始缓存 |
| 自动拆分判断错误 | 多信号评分、正规来源优先、原始数据可重算、低置信度通知 |
| Misaka 更新导致数据库不兼容 | 更新前一致性备份、迁移后冒烟测试、旧镜像与数据库联合回滚 |
| Cookie 泄漏或失效 | 0600 权限、日志脱敏、独立低权限账号建议、到期通知 |
| 公网 Token 被扫描 | HTTPS、长随机 Token、每设备隔离、调用限额、可快速吊销 |
| 备份与主机同时损坏 | 加密异地备份和定期真实恢复演练 |
| 高级弹幕效果丢失 | 原始字段尽量保留，并明确受播放器和兼容 API 能力限制 |

## 21. 已确认的决策

- 以最新版稳定版 Misaka 为核心。
- 使用 MySQL 持久化。
- 部署在用户达拉斯 VPS 的 Docker 中。
- 使用现有 Caddy 和 Cloudflare 域名。
- 播放器 API 公网访问，管理与内部控制接口受保护。
- 正常匹配和异常补档处理均以无人值守为目标。
- 低置信度也自动执行，不等待确认；通过通知和后台标记降低静默错误风险。
- 自动更新、健康检查、备份和失败回滚。
- 本阶段在当前工作区生成部署包，不直接改动 VPS。
